MaxDock · design system v2

maxdock-design-v2.html — what it looks like. Companions: MAXDOCK_FUNCTIONAL_SPEC.md (what it does) and MAXDOCK_ARCHITECTURE.md (how it is built).

Built for a shift, not a demo

The people using this are running shipping and receiving. They are often standing, often on a phone or an iPad on the floor, and they look at this dozens of times a shift. Every decision below serves reading it quickly and acting on it — nothing is here to be attractive.

01 · Brand

Blue leads, green stays with the mark

Sampled from your artwork. Blue is the wordmark colour and the larger share of the mark, so it becomes the interface colour. Green is reserved for the logo and never used in the UI — in an operations tool green has to mean “complete”, and the brand should not compete with a status.

Logo usage — one rule, no exceptions.
The teal badge with the knocked-out mark is the MaxDock identity. It is the only logo used anywhere in the application: rail, wall display, printed dock sheets, emails, PDFs, favicon.
The full Max Solutions logo appears on the login page and nowhere else, once, as ownership attribution. It is a wide two-colour lockup and it will not sit correctly in a 32px rail, a table header or a report footer — using it there breaks the spacing and the palette. --brand-green exists for that one placement only.

02 · Text size

Three sizes, one line of code

A person on the floor with a tablet at arm's length needs bigger text than someone at a desk. Every size in the system is derived from one --scale token, so the control below changes everything in proportion — nothing can drift or overlap. Saved per user in user_preferences, so it follows them between devices and shifts.

03 · The dock board

Doors across, hours down, always one screen

Doors are columns, so going from 6 doors to 15 narrows the columns rather than pushing the page taller. The time rows divide whatever height is left, which means slots are as tall as the screen allows and carry three lines instead of one. There is no vertical scrolling.

That makes the interval the control that decides whether a day fits. These are measured, not guessed — a 07:00–17:00 day, after the top bar, KPIs and board header:

IntervalRowsLaptop 1080iPad landscapeVerdict
2 hours5156px106pxRoomy. Best for wall displays.
1 hour1078px53pxDefault. Fits every device.
30 minutes2039px26pxOne line only, and scrolls on tablets.
15 minutes4019px13pxAlways scrolls. Use for one busy hour, not a day.

On the board, references are shortened. At 12 doors a column is about 74px, and MXD-000041 does not fit — it clips. So the board shows 41, the way a paper dock sheet does, and the full reference appears the moment you open the booking. Everyone on site already says “forty-one”.

05 · Why the old build had so many options

Keep every option. Put them in one place.

The options in the old build were not clutter — six sites run differently, and the settings existed because someone needed them. None of that should be lost. What went wrong was where they lived: five separate gear menus, each built by a different script, all fighting over the same corner of the screen. The fix is organisational, not a reduction.

Two homes, and only two. Preferences for how a person likes to work — reached from the avatar, applies everywhere, follows them between devices. Settings for how a site operates — in the rail under Administration, permission-gated. Every operational feature has an on/off so a site that does not want it never sees it. Nothing hides in a gear icon on a toolbar.

06 · Rules for whoever builds this

  1. One stylesheet. Never a maxdock-dbNN.css. A visual change edits a token.
  2. No !important. The old build had 3,874.
  3. Transitions use --motion. Never a literal duration, or prefers-reduced-motion stops working.
  4. No MutationObservers for layout. The old build ran 21 at once — that is what duplicated the gears.
  5. Every script declared in the HTML. The old config file injected 33 stylesheets and 23 scripts at onload, so the real load order was invisible.
  6. Sizes come from --scale. Never a literal px in a component rule, or the text-size control breaks.
  7. The board never scrolls vertically. Rows are 1fr. If it scrolls, the interval is wrong, not the CSS.
  8. Monospace means spoken aloud. Times, doors, references, skid counts, POs.
  9. Fields are only as wide as their content. Use .field--xs/sm/md/lg width caps and .fieldFlow so short fields sit back-to-back. Never a page of full-width half-empty inputs.
  10. Password fields have a show/hide toggle (.passwordReveal), 44px, inside the field. The button swaps type between password and text and its aria-label between Show and Hide.
  11. Touch targets are var(--tap), 44px minimum. Applied to every button, input, select and text-only action. Padding and type are unchanged — only the hit area grows. Enforced by a11y.tap-target in the checker.
  12. Every option has an off switch, and lives in Preferences or Settings — nowhere else.
  13. Customers see nothing internal. No door names, no other companies. Enforced in the RPCs, mirrored in the UI.
  14. Refresh never interrupts. The 5-second poll must not re-render a slot picker mid-selection.
  15. Generate the QR locally. Never a third-party service.
  16. One logo in the app. The teal badge, everywhere. The full Max Solutions lockup appears on the login page only.
