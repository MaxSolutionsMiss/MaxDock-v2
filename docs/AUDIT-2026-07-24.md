## 4. CI enforcement — pass, and better than what I specified

I asked for a workflow that runs the checker. What was built reads the stage number out of
`STATUS.md` and escalates automatically:

```
stage 0  + checker fails  → ::warning, exit 0
stage 1+ + checker fails  → exit 1, build fails
```

I tested both paths. The `awk` parses `0` correctly from the current file. Rewriting the stage
line to `1 of 8` and re-running produces **exit 1** — enforcement arms itself the moment the
implementer writes "Stage 1", with no separate switch anyone has to remember. That is a better
design than the flat workflow in the bridge document, and I would keep it.

The second checker, `verify-maxdock-implementation.mjs`, is implementation-owned as agreed, runs
clean (34 warnings, all `transition.legacy-shell` on the React files), and correctly stays out of
the design-owned checker's way.

`scripts/test-verifiers.mjs` passes on all four cases — both checkers against both a clean and a
deliberately bad fixture. **Testing the tests was not asked for and is the right instinct.** A
checker nobody has proven can fail is decoration.

## 5. The React/Vite shell — acceptable, with the risk named

The repository currently contains 12 `.tsx` files, 4 `.ts` files, Vite, React Router and an ESLint
config. The architecture document specifies a static, no-build, vanilla application with no
bundler. On the face of it that is a direct contradiction.

It is not, because it is declared. `README.md` states plainly that the deployed React app is *"a
temporary visual foundation only… not the approved production architecture and must not receive
additional operational features"*, and lists *"no React, Vite, npm or bundler in the production
replacement"* among the implementation rules. `STATUS.md` says the same. The contradiction is
documented rather than hidden, and the implementation gate flags every React file as a transition
warning so the count is visible in CI.

That is the correct handling. **The risk worth naming out loud: "we will replace it in Stage 1" is
exactly how the previous codebase started.** Every layer in the old MaxDock was temporary when it
was written. The protection here is that the shell has no operational features to become
load-bearing, and that Stage 1 deletes `src/` entirely. Hold that line.

## 6. One hardening recommendation

**The Stage 0 bypass is self-declared and has no expiry.** The workflow decides whether to block
purely from a number in a file the implementer controls. If `STATUS.md` stays at `0 of 8` while
Stage 1 code lands, CI never blocks and nobody is told.

I am not suggesting that would be done deliberately. It is the kind of thing that happens because
a stage runs long and updating the header is the last thing on the list.

Suggested change — make the bypass conditional on the shell still being the only thing there:

```yaml
- name: Stage 0 bypass is void once Stage 1 work exists
  shell: bash
  run: |
    if [[ "${{ steps.stage.outputs.number }}" == "0" ]] \
       && { [[ -d js ]] || [[ -d app ]] || [[ -f assets/maxdock.css ]]; }; then
      echo "Stage 1 directories exist but STATUS.md still says Stage 0."
      echo "Update docs/STATUS.md — the conformance bypass no longer applies."
      exit 1
    fi
```

Then the bypass cannot outlive the condition that justified it. `js/`, `app/` and
`assets/maxdock.css` are all confirmed absent right now, so this can be added today and will pass.
